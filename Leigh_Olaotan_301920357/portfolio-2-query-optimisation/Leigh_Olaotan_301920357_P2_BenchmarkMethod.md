# Benchmark method

This synthetic experiment uses the P1 schema in a separate `mit8103_benchmark` database on the same PostgreSQL 17.11 container. The 39-row P1 fixture is unchanged. Run [BenchmarkData.sql](Leigh_Olaotan_301920357_P2_BenchmarkData.sql) only after the P1 schema in empty benchmark tables. It refuses nonempty tables and the named P1 database. [Load output](Leigh_Olaotan_301920357_P2_BenchmarkDataOutput.txt) records actual counts.

## Dataset and workloads

The fixed data set contains 1,030,100 rows. It has 10,000 customers, 100 products and 300,000 orders. Each order has two lines, giving 600,000 lines.

There are 120,000 full payments. One order occurs per minute from 1 January 2024 UTC. Customers rotate evenly, giving 30 orders each.

Each tenth order is cancelled; even-numbered placed orders are paid. Two product choices and quantities are generated by stated modular formulas. Prices are fictional, positive NGN values and payments equal historical line totals.

Stored stock is an assumed available quantity. The experiment did not replay stock reservations. Opening stock would equal available stock plus quantities on placed orders.

This regular distribution is reproducible but not representative of seasonal demand or popular customers/products. Status is correlated with the customer rotation; the chosen customer is in the placed group. No production-scale generalisation is made.

[BenchmarkQueries.sql](Leigh_Olaotan_301920357_P2_BenchmarkQueries.sql) defines both unchanged workloads:

1. `selective_history`: the ten newest orders for customer BC00042 between 1 April (inclusive) and 1 July 2024 UTC (exclusive). The range contains 13 orders; LIMIT returns ten. The unique customer-code lookup is included in the plan. The proposed index is `(customer_id, ordered_at DESC, order_id DESC)` on sales_order, matching equality, range and deterministic ordering.
2. `broad_status`: count all placed orders, returning 270,000 (90% of orders). A customer/date index is not designed to answer this predicate. This second workload bounds the benefit claimed for the index.

## Measurement controls

The submitted [Python runner](Leigh_Olaotan_301920357_P2_Benchmark.py) requires only Python 3's standard library and Docker/psql. It tests dataset counts, candidate-index presence, the exact expected query results and the query-source hash. It saves the full index definitions and server/settings metadata. Before baseline capture, VACUUM ANALYZE is run once on all five tables. No rows or statistics are intentionally changed between phases; only the candidate index is added.

Each phase tests results, then performs one discarded warm-up and five measured `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)` runs for each workload. One extra text-plan execution per workload is labelled diagnostic and is excluded from the timing sample. CSV values are server-reported execution/planning times, not Docker startup/network wall time. Medians use the five execution times only. The JSON keeps each warm-up/measured plan and buffer count.

Both phases use UTC, JIT off and `max_parallel_workers_per_gather=0` to reduce parallel-worker variation. The planner's scan methods remain enabled; no scan is forced. Settings are identical across phases and recorded, including work_mem/shared_buffers/cost settings.

Data tests and warm-up runs access the tables before measurement. The tests do not control disk caching. They do not prove that all data stays in memory.

The observed 400 KiB shared buffer pool still causes buffer reads; OS caching is unmeasured. See the after-phase analysis for this observed limitation. No cache flush is claimed.

Other host activity and short-query timing noise remain limitations. Five runs describe this local sample, not statistical confidence or a service latency guarantee.

## Reproduce baseline

From repository root, use a new database name if the example already exists. These commands show the initial one-time setup; do not reload an existing benchmark:

```sh
docker exec mit8103-postgres createdb -U mit8103_admin mit8103_benchmark
docker exec -i mit8103-postgres psql -X -v ON_ERROR_STOP=1 -U mit8103_admin -d mit8103_benchmark \
  < Leigh_Olaotan_301920357/portfolio-1-database-design/Leigh_Olaotan_301920357_P1_Schema.sql
docker exec -i mit8103-postgres psql -X -v ON_ERROR_STOP=1 -U mit8103_admin -d mit8103_benchmark \
  < Leigh_Olaotan_301920357/portfolio-2-query-optimisation/Leigh_Olaotan_301920357_P2_BenchmarkData.sql
python3 Leigh_Olaotan_301920357/portfolio-2-query-optimisation/Leigh_Olaotan_301920357_P2_Benchmark.py \
  before --output-dir temp/logs/p2-new-before
```

Use `--docker /path/to/docker` if Docker is not on PATH. Replace this example path with the installed executable. Use `--database NAME` for a new isolated replay. The runner refuses to overwrite phase files. Save the baseline output before applying the index. Then follow [the indexed measurement instructions](Leigh_Olaotan_301920357_P2_PerformanceAnalysis.md#reproduce-the-after-phase). Do not drop an index from an operational database to imitate a baseline.
